# Tutorial video recorder

Records a scripted walkthrough of a web app (against your local dev server) as a video with an
animated cursor, click highlighting, and auto-zoom on each click. The core recorder is vendored
from a third-party skill — see [`NOTICE.md`](./NOTICE.md) for provenance/license.

## Prerequisites

- `playwright` (a dependency of this package) with Chromium installed
  (`npx playwright install chromium`)
- `ffmpeg` on PATH — **mandatory**, not just for auto-zoom. `record.mjs` captures individual
  JPEG frames itself (`page.screencast.start({ onFrame })`) rather than letting Playwright mux
  a video internally (`{ path }`), and assembles them into the output with ffmpeg. See
  [Output format](#output-format) for why.
- Your project's local dev server running, at whatever URL your scenario's `start` points to

Check with:

```bash
node .recordings/tooling/record.mjs --check-prereqs
```

## Where output goes

Each video is a **flow** — a folder at `.recordings/flows/<name>/` holding its scenario
files, an optional `setup.mjs`, a `record.mjs`, and a `README.md`. Those are tracked in git.
Generated video files go in that flow's `.output/`, which is gitignored since they're large
binaries; the recorder creates it. The `create-flow` skill authors a flow and `record-flow`
re-runs one. Saved sign-in sessions live in `.recordings/auth/`, shared
across flows and also gitignored. This is separate from `.scratchpad/`, which is for throwaway
POC work — `.recordings/` is for videos you're actually keeping around.

## 1. Save a signed-in session (once)

`record.mjs` never accepts credentials directly — a scenario file should stay safe to commit.
Generate a Playwright `storageState` file instead: write a one-off script following the shape in
[`references/auth.md`](./references/auth.md), and save the output to
`.recordings/auth/<account>.auth.json` (gitignored) — it can impersonate whatever account
signed in.

## 2. Write a scenario

A JSON file describing the start URL and every step, in order. See
[`references/effects.md`](./references/effects.md) for the full step/effects reference
(`click`, `type`, `select`, `press`, `wait`, `goto`; `role`/`selector`/`text`/`label` locators;
per-step `caption` overrides; `captionPlacement`).

**This repo's default: captions off.** The evaluation in the PRD/POC concluded a clean
cursor + zoom (no text on the page itself) reads closer to the Screen Studio look we're going for
than captions drawn over the recording — set `"effects": { "captions": false }`. The text viewers
read lives outside the page: the presentation's [narration](./references/narration.md), a line,
header and glow on the stage around the recording.

```json
{
  "url": "http://localhost:3000/",
  "effects": { "captions": false },
  "auth": { "expect": { "role": "button", "name": "Account" } },
  "steps": [
    { "action": "click", "selector": "a[href*=\"/settings\"]" },
    { "action": "type", "selector": "[placeholder=\"Search\"]", "text": "Hello world" },
    { "action": "press", "keys": "Enter" }
  ]
}
```

## 3. Record

```bash
node .recordings/tooling/record.mjs \
  --scenario path/to/scenario.json \
  --out path/to/output.webm \
  --storage-state path/to/auth.json
```

Writes `output.webm`, `output.clicks.jsonl`, and `output.zooms.json`.

## 4. Apply auto-zoom

```bash
node .recordings/tooling/render-auto-zoom.mjs \
  --video path/to/output.webm \
  --zooms path/to/output.zooms.json \
  --out path/to/output-zoomed.mp4
```

Decoupled from recording on purpose — record once, decide on zoom (or re-render it
differently) without re-driving the browser.

## 5. Multi-screen presentation (optional)

For a "change something here, here's what happens there" video: record each screen as its own
scenario (one desktop, one `"device": "phone"`, however many you need — see
[Recording multiple screens at once](#recording-multiple-screens-at-once) below for keeping them
in sync), then wrap them in device frames and composite them together:

```bash
node .recordings/tooling/presentation/compose.mjs \
  --screens screens.json \
  --out path/to/presentation.mp4 \
  --header "What this video shows"
```

`screens.json` is an array, one entry per screen:

```json
[
  { "name": "desktop", "label": "Desktop", "frame": "desktop", "clip": "path/to/desktop.mp4" },
  { "name": "mobile", "label": "Mobile", "frame": "mobile", "clip": "path/to/mobile.mp4" }
]
```

`frame` is one of `desktop | mobile | mac | windows | chrome | custom | none` (run
`compose.mjs --help` for the full reference, including how `custom` works). Any number of
screens is fine — the stage zooms the whole row to fit.

`--header` is a one-line title shown top-center (optional); `--wordmark` shows a small brand
mark above it (also optional — neither is shown unless you pass it). To tune the header or
layout without recording, run the same command with `--preview` in place of `--out`: it serves
the stage and prints a URL to open in a browser (clips are optional there and fill the screens
if given). Without `--header`, the preview shows a sample title so you can judge the layout.
`stage.html` is re-read on every refresh.

The strip under the screens shows the flow's **narration**: lines set with a `narration` field on
scenario steps, written to `<clip>.narration.json` by `record.mjs` and picked up by `compose.mjs`
automatically. See [`references/narration.md`](./references/narration.md).

This re-records [`presentation/stage.html`](./presentation/stage.html) (each input clip plays as
a native `<video>` element inside a CSS-drawn frame) through the same recorder as everything else
here — the frames/labels/layout are all just CSS and a small amount of DOM-building JS in that
one file, easy to reskin without touching any compositing code.

### Recording multiple screens at once

`record.mjs` exports `prepareRecording()` (navigation/sign-in) and `captureRecording()`
(starts the screencast, runs the scenario) separately, not just the combined
`recordWalkthrough()`. Two things need aligning across screens recorded concurrently:

- **Starting together.** Setup duration varies a lot between e.g. a real signed-in session
  restore and an anonymous page load — starting each screen's screencast whenever *that screen's
  own* setup happens to finish produces a real, measurable wall-clock offset. Fix: call
  `prepareRecording()` for every screen via `Promise.all` first, *then* `captureRecording()` for
  every screen via `Promise.all`, so every screencast starts within the same tick.
- **Ending together.** One screen's scenario can finish its steps before another's. Fix: pass a
  shared `createRecordingSyncBarrier(participantCount)` to every `captureRecording()` call as
  `{ sync: barrier }` — each call marks itself done and then waits for every other screen to
  finish its own steps before any of them starts its tail padding, so they all end at the same
  point instead of trailing off one by one.

```js
import { prepareRecording, captureRecording, createRecordingSyncBarrier } from "./record.mjs";

const optionsPerScreen = [optionsA, optionsB, optionsC]; // any number
const prepared = await Promise.all(optionsPerScreen.map(prepareRecording));
const sync = createRecordingSyncBarrier(prepared.length);
const recorded = await Promise.all(prepared.map((p) => captureRecording(p, { sync })));
```

## Output format

Every mp4 the recorder writes is a finished, postable video — there is no separate export step:

- H.264 High level 4.2, 4:2:0, limited-range BT.709, progressive
- 30 fps constant, a keyframe every 2s with closed GOPs, `moov` atom first (plays while downloading)
- audio: the recorder's own clips are silent, and every finished video carries one AAC track,
  48 kHz stereo: the house music (see [Music](#music))
- a side-by-side presentation is exactly 1920x1080 (16:9). A single-screen recording keeps its
  viewport size, so record it at 1920x1080 if it will be posted

The format lives in [`delivery-format.mjs`](./delivery-format.mjs). After every encode the file is
probed and the recording fails if anything above doesn't hold (`compose.mjs` also checks the frame
is 1920x1080), so an mp4 that exists meets the format. To check a file by hand:

```bash
node .recordings/tooling/delivery-format.mjs --check video.mp4 --size 1920x1080
```

The recorder used to write lossless 4:4:4 at 60 fps instead. That format doesn't decode in most
browsers, phones, QuickTime or hardware players (so it fails to play or upload on Discord, X,
LinkedIn, Instagram and the like) and produced files of tens to hundreds of MB. At CRF 18 with
`slow` the flat-color UI content encodes to a few MB with no visible loss, so quality is traded
away only at the final encode, once.

### Music

**Every finished video has the same quiet background track.** Nothing in a flow needs to ask for it:

- **The track** is the one audio file in [`../music/`](../music/). To change it for every video,
  swap that file. More than one file there is an error, since nothing says which to use. Keep a note
  of the track's source and license beside it; whether it is free to use is yours to confirm.
- **Where it is added.** At the end of `recordWalkthrough`, so a side-by-side presentation
  (`compose.mjs` records its stage through it) and a single-screen recording both get it. The clips
  that only feed a presentation's stage (`-desktop`, `-window`, `-mobile`) stay silent.
- **What is done to it** ([`music.mjs`](./music.mjs)): cut to the video's length (looped if it is
  shorter), levelled to **-26 LUFS** integrated, faded in over 1s and out over 2s, encoded as AAC.
  The video stream is copied untouched. -26 LUFS is a bed, far under a normal standalone video
  (-14 to -16): it should sit under the on-screen text without being noticed. It is a constant,
  `MUSIC_LOUDNESS_LUFS`, if it needs nudging.
- **Opting out.** `--no-music` on `record.mjs`, or `music: false` in the options to
  `recordWalkthrough`. `music: "path/to/other.mp3"` uses another track for one video.
- **An existing video** gets the track, replacing any audio it has, with
  `node .recordings/tooling/music.mjs video.mp4`.
- **Checking it.** The finished video has an `aac` stream (`ffprobe -v error -show_entries
  stream=codec_name -of csv=p=0 video.mp4`) and measures about -26 LUFS
  (`ffmpeg -hide_banner -nostats -i video.mp4 -vn -af ebur128 -f null -`, the `I:` line under
  Summary).

`presentation/stage.html` is a fixed 1920x1080 frame; its layout is designed on an 1800x950 canvas
that is scaled to the frame width and centered vertically. The canvas has an explicit vertical
budget (header, then the row of screens, then a fixed-height zone at the bottom for
[narration](./references/narration.md#layout)) — the row of screens zooms down to fit whatever
count and frame types you give it, so the narration zone's size never depends on layout.

**Why `record.mjs` uses `onFrame` instead of `{ path }`:** letting Playwright mux the video
internally (the `{ path }` option) routes every frame through Playwright's own VP8 encoder
first, with fixed settings the public API doesn't expose — the block-seam artifacting this caused
was traced to that internal muxing step, present even with `quality: 100`. `onFrame` hands us the
raw JPEG bytes directly, before that muxer ever sees them, so `record.mjs` writes each frame to
disk itself and assembles them into a temporary lossless capture (`assembleFramesToVideo()`, full
range 4:4:4). That capture is only ever an input: the lossy steps in the whole pipeline are each
frame's own JPEG compression (`quality: 100`) and the one delivery encode at the end.

**The 4:2:0 conversion happens once, at the very end.** Every filter chain ends with
`DELIVERY_FILTER_TAIL`, which converts the full-range 4:4:4 frames to limited-range 4:2:0 only
after zooming and scaling are done, so no earlier stage throws chroma away. The color tags are set
with `setparams` (and matching x264 params), not bare `-color_range`/`-color_primaries` output
flags, which libx264's ffmpeg wrapper only partially honors. Limited range with complete tags is
what players expect: full-range tagging is one of the things that makes some decoders show washed
out or crushed colors, notably near-black UI backgrounds like this app's `#0b0c0d`.
